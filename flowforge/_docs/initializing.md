# FlowForge — Design Specification v1.1

> Annotation-Based AI Agent Framework  
> Version 1.1 | April 2026

This file is a design-oriented companion to the API reference. It explains the
concepts FlowForge is built around: decorator-defined structure, DAG
compilation, typed data flow, generated planning docs, tools, skills, dynamic
generation, and execution tracing.

---

## 1. Overview

FlowForge is a Python package for building AI agent systems with decorators
instead of manual graph construction. Users define agent structure with
`@global_config`, `@flow`, `@task`, and `@step`. FlowForge compiles that
metadata into a DAG, validates it, and executes it with async runners.

The planner can use the DAG and generated docs as a map of available
capabilities. In autonomous or hybrid mode, it can select an execution route;
when `dynamic_flow=True`, it can also ask FlowForge to generate missing flows.

### Design Principles

- **Annotation-first**: agent structure lives in Python decorators.
- **Type-aware data flow**: Pydantic models define I/O contracts where needed.
- **DAG-native**: the annotation tree compiles into a graph with cycle checks
  and route resolution.
- **Dual-prompt model**: each node has a user-written `prompt` for execution
  and an AI-generated `doc` for planning metadata.
- **Recursive nesting**: flows can contain flows, and tasks can contain tasks.
- **Tool-agnostic integration**: MCP, HTTP, Python functions, Claude Skills,
  and local Agent Skills share a common `tools=[...]` surface.
- **Dynamic extension**: missing capabilities can be generated, persisted,
  cached, and reused.

## 2. Prompt And Doc

Every annotation can carry two kinds of text.

### `prompt`

`prompt` is written by the user. It describes what the node should do at
runtime.

```python
@step(order=1, prompt="Detect the document format and validate the input")
async def validate_input(ctx):
    ...
```

### `doc`

`doc` is generated by FlowForge's doc generation system. It summarizes the
node for planning and discovery.

A doc can include:

| Field | Meaning |
|-------|---------|
| `summary` | Short description of the node's role |
| `input_schema_desc` | Field-level explanation of the input schema |
| `output_schema_desc` | Field-level explanation of the output schema |
| `preconditions` | Conditions required before the node can run |
| `capabilities` | Capabilities the node provides |
| `children_overview` | Summary of child flows/tasks/steps |
| `routing_hints` | Branch or route selection hints |

Example user annotations:

```python
@flow(name="data_pipeline", prompt="Collect, clean, and transform external data")
class DataPipeline:
    @task(name="ingest", prompt="Fetch raw data from external sources")
    class IngestTask:
        ...

    @task(name="transform", prompt="Transform cleaned data for downstream use")
    class TransformTask:
        ...
```

Example generated doc:

```json
{
  "node": "flow:data_pipeline",
  "doc": {
    "summary": "Collects, cleans, and transforms external data.",
    "input_schema_desc": {
      "source_url": "URL of the data source",
      "format_hint": "Optional expected format"
    },
    "output_schema_desc": {
      "records": "Transformed records",
      "metadata": "Processing statistics"
    },
    "preconditions": ["A valid source_url is provided"],
    "capabilities": ["CSV parsing", "JSON parsing", "schema normalization"],
    "children_overview": "ingest -> transform"
  }
}
```

## 4. Annotation Hierarchy

```text
@global_config
└─ @flow
   ├─ @flow
   │  └─ @task
   │     └─ @step
   └─ @task
      ├─ @task
      │  └─ @step
      └─ @step
```

| Parent | Allowed children | Notes |
|--------|------------------|-------|
| `@global_config` | root `@flow` classes | One top-level agent config |
| `@flow` | `@flow`, `@task` | Flows can nest recursively |
| `@task` | `@task`, `@step` | Container tasks hold child tasks; leaf tasks hold steps |
| `@step` | none | Atomic executable unit |

Branch dispatch is not represented by a separate public decorator. It is
configured with `condition`, `branches`, and `fallback` on `@step`, `@task`,
or `@flow`.

## 5. Core Annotation Parameters

### `@global_config`

```python
@global_config(
    prompt="You are a data-processing assistant.",
    llm_config=LLMConfig.for_claude(temperature=0.3),
    tools=[MCPServer(url="https://api.example.com/mcp", name="search")],
    dynamic_flow=True,
)
class MyAgent:
    ...
```

| Parameter | Description |
|-----------|-------------|
| `prompt` | Global system prompt |
| `llm_config` | Default provider/model configuration |
| `tools` | Global tools and skills |
| `dynamic_flow` | Enables runtime flow generation |

### `@flow`

```python
@flow(
    name="data_pipeline",
    prompt="Collect and transform data",
    input_schema=RawDataInput,
    output_schema=ProcessedData,
    depends_on=["auth"],
    max_retries=3,
)
class DataPipeline:
    ...
```

| Parameter | Description |
|-----------|-------------|
| `name` | Stable flow identifier |
| `prompt` | Flow role and behavior |
| `input_schema` / `output_schema` | Optional Pydantic I/O contracts |
| `depends_on` | Cross-flow dependency names |
| `max_retries` | Retry count for failed execution |
| `condition`, `branches`, `fallback` | Optional branch dispatch |

### `@task`

```python
@task(
    name="retry_task",
    prompt="Keep trying until valid",
    max_loops=5,
    loop_condition=lambda output: output.get("valid", False),
)
class RetryTask:
    ...
```

| Parameter | Description |
|-----------|-------------|
| `name` | Stable task identifier |
| `prompt` | Task role and behavior |
| `input_schema` / `output_schema` | Optional Pydantic I/O contracts |
| `max_retries` | Retry count |
| `on_error` | Error behavior such as `"raise"` or `"skip_remaining"` |
| `max_loops` / `loop_condition` | Retry-with-condition loop |
| `condition`, `branches`, `fallback` | Optional branch dispatch |

### `@step`

```python
@step(
    order=1,
    prompt="Validate the input schema",
    input_schema=RawDoc,
    output_schema=ValidatedDoc,
    timeout_seconds=30,
)
async def validate_schema(ctx):
    ...
```

| Parameter | Description |
|-----------|-------------|
| `order` | Execution order within a leaf task |
| `prompt` | Step system prompt |
| `input_schema` / `output_schema` | Runtime Pydantic validation schemas |
| `tools` | Step-local tools and skills |
| `timeout_seconds` | Execution timeout |
| `unique` | Same-order group selection |
| `condition`, `branches`, `fallback` | Optional branch dispatch |

## 6. Ordering And Parallelism

If `order=None`, siblings are auto-sequenced in declaration order. If siblings
share the same explicit integer `order`, they form a parallel execution group.

```python
@task(name="fetch", prompt="Fetch from two sources")
class FetchTask:
    @step(order=1, prompt="Fetch source A")
    async def a(ctx): ...

    @step(order=1, prompt="Fetch source B")
    async def b(ctx): ...

    @step(order=2, prompt="Merge")
    async def merge(ctx): ...
```

`unique=True` means only that node runs within its same-order group. Multiple
`unique=True` nodes at the same order raise an order conflict.

## 7. Data Flow

Data is threaded through the hierarchy:

```text
engine.run(input)
  -> flow input
  -> child flow/task input
  -> step ctx.input
  -> step return value
  -> next step/task/flow input
  -> final result
```

Step input and output validation happens when schemas are declared. Flow and
task schemas document and guide contracts; step boundaries are the strictest
runtime validation points.

## 8. Tools And Skills

FlowForge supports five tool families:

| Type | Behavior |
|------|----------|
| `FunctionTool` | Local Python function executed by FlowForge |
| `HTTPTool` | HTTP request executed by FlowForge |
| `MCPServer` | Remote MCP tool schema/call integration |
| `ClaudeSkill` | Anthropic-native Skills API via `container.skills` |
| `AgentSkill` | Local standard `SKILL.md` loaded into the prompt |

Tools are registered at any hierarchy level:

```python
@global_config(
    prompt="Engineering assistant",
    tools=[
        FunctionTool(func=calculate, name="calculator"),
        ClaudeSkill(name="pptx"),
        AgentSkill(path=".agents/skills/code-review"),
    ],
)
class Agent:
    ...
```

Inside `ctx.call_llm()`, angle-bracket references select tools:

```python
await ctx.call_llm("Solve this with <calculator> and review with <code-review>")
```

`ClaudeSkill` is Anthropic-only. `AgentSkill` is provider-neutral because it
injects local `SKILL.md` instructions into the model context.

## 9. Dynamic Flow Generation

When `dynamic_flow=True`, autonomous/hybrid planning can generate missing
flows. The internal `_dynamic_generator` meta-flow:

1. confirms that a real capability gap exists;
2. builds a code-generation brief;
3. asks the LLM for FlowForge decorator code;
4. runs AST safety validation;
5. compiles the generated class;
6. persists it to `manifest.json` if configured;
7. injects it into the DAG;
8. replans and executes.

Generated flows are cached. With `persist_generated=True` and
`auto_load_generated=True`, later compiles load the manifest before planning,
and generation is skipped when the flow already exists in the DAG or manifest.

## 10. Execution Lifecycle

```text
Decorate
  -> Compile
  -> Generate docs, optionally
  -> Plan, optionally
  -> Generate missing flows, optionally
  -> Execute
  -> Trace
```

After execution, `engine.last_trace` stores per-node timing, status, selected
branches, and executed-path information. The trace can be rendered with
Mermaid or Graphviz through the visualization APIs.

---

## 11. Error Handling

| Mechanism | Behavior |
|-----------|----------|
| `max_retries` | Retries failed flow/task execution |
| `timeout_seconds` | Bounds step execution time |
| `on_error="raise"` | Propagates the error |
| `on_error="skip_remaining"` | Returns the last successful step output when possible |
| schema validation | Raises execution errors for invalid I/O |
| AST safety validation | Blocks unsafe generated code before execution |
